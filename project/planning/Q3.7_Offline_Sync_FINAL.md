## Overview

**What:** Complete offline mode support allowing users to continue using the app without internet connection. All core features work offline with intelligent data caching, queued sync, and conflict resolution.

**Why:** Mobile users frequently experience poor connectivity (subway, rural areas, airplane mode, poor cell signal). Offline support ensures uninterrupted user experience and prevents frustration. Key stat: Users lose 30% of logged data when apps don't support offline mode.

**When:** Offline mode automatically activated when network unavailable. Transparent to user with minimal UI changes (status banner only). Syncs automatically when connection restored.

**Dependencies:**
- All Q3.x specifications (offline support affects every feature)
- Local device storage (AsyncStorage for React Native)
- Background sync capability (when app backgrounded/closed)
- Network state detection APIs

**Goals:**
- 100% of logging features work offline (meals, workouts, weight)
- 95% of read features work offline (view plans, history, favorites)
- Zero data loss during offline periods
- <10 second sync time when reconnected (for typical 24h offline)
- Transparent UX (user barely notices offline state)

## Sync Strategy

### Sync Triggers

**1. App Launch**
- Immediate sync on app open (if online)
- Fetch latest data from server
- Upload queued actions
- Update local cache
- Duration: <5 seconds typical

**2. Connection Restored**
- Detect network state change (offline → online)
- Auto-trigger sync
- Show progress indicator
- Toast on completion: "Synced ✓"

**3. Background Sync**
- iOS: Use Background Fetch API (every 15-30 min when app backgrounded)
- Android: Use WorkManager (every 15 min)
- Syncs queued actions only (no downloads)
- Silent (no UI feedback)

**4. Manual Sync**
- Pull-to-refresh gesture on Home tab
- Sync button in Settings → Account
- Forces immediate sync
- Shows loading spinner

**5. After Mutations**
- After user logs meal/workout/weight (while online)
- Immediate sync (optimistic UI update + background sync)
- If fails → Retry 3x with exponential backoff

---

### Sync Phases

**Phase 1: Upload Queued Actions (Priority)**
```
1. Dequeue all pending actions (FIFO order)
2. Group by type (logs, edits, deletes, favorites)
3. Upload in order:
   a. Deletes (clean up first)
   b. Edits (update existing)
   c. New logs (create new)
   d. Favorites (metadata updates)
4. Retry failed actions (3x with backoff)
5. Mark successful actions as synced
6. Remove from queue
```

**Duration:** 2-5 seconds for 24h of offline actions

---

**Phase 2: Download Fresh Data**
```
1. Fetch current week meal/workout plans
2. Fetch last 3 weeks of history
3. Fetch saved items (favorites)
4. Fetch progress data (weight, summaries, streaks)
5. Fetch AI insights (if expired)
6. Update local cache
```

**Duration:** 3-5 seconds

---

**Phase 3: Reconciliation**
```
1. Compare server data with local cache
2. Detect conflicts (same entry edited locally and on server)
3. Apply conflict resolution rules (see Conflict Resolution section)
4. Merge data
5. Update UI
```

**Duration:** 1-2 seconds

---

**Total Sync Time:** <10 seconds for typical 24h offline period

## Queue Management

### Queue Data Structure

```typescript
interface SyncQueueItem {
  id: string; // Unique queue item ID
  action_type: 'create' | 'update' | 'delete';
  resource_type: 'meal' | 'workout' | 'weight' | 'profile' | 'grocery_item' | 'saved_item';

  // The actual data payload
  payload: {
    endpoint: string; // API endpoint to call
    method: 'POST' | 'PUT' | 'DELETE';
    body?: any; // Request body
    local_id?: string; // Temporary ID for new items
  };

  // Metadata
  created_at: Date; // When action was queued
  retry_count: number; // How many times we've tried to sync
  last_retry_at?: Date;
  priority: 'critical' | 'high' | 'normal' | 'low';
  status: 'pending' | 'syncing' | 'failed' | 'synced';
  error_message?: string;

  // Dependencies (must wait for other items to sync first)
  depends_on?: string[]; // Array of queue item IDs that must complete first
}
```

### Queue Operations

**1. Enqueue Action**
```javascript
async function enqueueAction(action) {
  const queueItem = {
    id: generateUUID(),
    action_type: action.type,
    resource_type: action.resource,
    payload: action.payload,
    created_at: new Date(),
    retry_count: 0,
    priority: determinePriority(action),
    status: 'pending',
    depends_on: action.dependsOn || []
  };

  // Add to local queue (AsyncStorage)
  await addToQueue(queueItem);

  // If online, attempt immediate sync
  if (isOnline()) {
    await syncQueue();
  }
}
```

---

**2. Dequeue and Sync**
```javascript
async function syncQueue() {
  // Get all pending items, sorted by priority and created_at
  const queue = await getQueue();
  const pending = queue
    .filter(item => item.status === 'pending' || item.status === 'failed')
    .sort((a, b) => {
      // Sort by priority first
      const priorityOrder = { critical: 0, high: 1, normal: 2, low: 3 };
      if (priorityOrder[a.priority] !== priorityOrder[b.priority]) {
        return priorityOrder[a.priority] - priorityOrder[b.priority];
      }
      // Then by creation time (FIFO)
      return a.created_at - b.created_at;
    });

  for (const item of pending) {
    // Check dependencies
    const dependenciesSynced = await checkDependencies(item.depends_on);
    if (!dependenciesSynced) {
      continue; // Skip for now, will retry later
    }

    // Update status
    item.status = 'syncing';
    await updateQueueItem(item);

    try {
      // Execute API call
      const result = await executeQueueItem(item);

      // Success
      item.status = 'synced';
      await removeFromQueue(item.id);

      // Update local data if needed (e.g., replace local_id with server_id)
      if (result.server_id && item.payload.local_id) {
        await updateLocalId(item.payload.local_id, result.server_id);
      }
    } catch (error) {
      // Failure
      item.status = 'failed';
      item.retry_count++;
      item.last_retry_at = new Date();
      item.error_message = error.message;
      await updateQueueItem(item);

      // If max retries exceeded, mark as permanently failed
      if (item.retry_count >= 3) {
        await notifyUser(`Failed to sync ${item.resource_type}. Please try manually.`);
        await moveToFailedQueue(item);
      }
    }
  }
}
```

---

**3. Retry Failed Actions**
```javascript
async function retryFailedActions() {
  const queue = await getQueue();
  const failed = queue.filter(item => item.status === 'failed' && item.retry_count < 3);

  for (const item of failed) {
    // Exponential backoff: Wait 2^retry_count minutes
    const waitTime = Math.pow(2, item.retry_count) * 60 * 1000; // in ms
    const timeSinceLastRetry = Date.now() - (item.last_retry_at?.getTime() || 0);

    if (timeSinceLastRetry >= waitTime) {
      item.status = 'pending'; // Reset to pending for retry
      await updateQueueItem(item);
    }
  }

  // Trigger sync
  await syncQueue();
}
```

## Conflict Resolution

### Conflict Scenarios

**1. Same Entry Edited Locally and on Server**
- **Example:** User edits meal calories offline. Meanwhile, admin corrects calories on server.
- **Resolution:** Last-write-wins (LWW)
  - Compare `updated_at` timestamps
  - Keep most recent version
  - Notify user: "Your edit to [Meal Name] was overwritten by a server update."

---

**2. Entry Deleted Locally, Edited on Server**
- **Example:** User deletes workout offline. Server edits workout (e.g., admin correction).
- **Resolution:** Deletion wins
  - User intent to delete is stronger
  - Proceed with deletion
  - Log conflict for analytics

---

**3. Entry Created Offline, Duplicate Exists on Server**
- **Example:** User logs meal offline. Exact same meal (name, calories, time) logged on another device.
- **Resolution:** Merge with duplicate detection
  - Check for duplicates: Same resource_type, name, date, logged_at within 5 minutes
  - If duplicate found → Skip creation, update UI to use server ID
  - If not duplicate → Create as new entry

---

**4. Profile Edited Offline and Online**
- **Example:** User changes dietary restrictions offline. Another device changes activity level.
- **Resolution:** Field-level merge
  - Merge non-conflicting fields (dietary_restrictions from offline, activity_level from online)
  - For conflicting fields (same field edited both places) → Last-write-wins
  - Trigger meal plan regeneration if relevant fields changed

---

### Conflict Detection Algorithm

```javascript
async function detectConflicts(queueItem, serverData) {
  const localTimestamp = queueItem.payload.updated_at;
  const serverTimestamp = serverData.updated_at;

  // No conflict if server data is older
  if (serverTimestamp < localTimestamp) {
    return { hasConflict: false };
  }

  // Conflict detected
  return {
    hasConflict: true,
    localData: queueItem.payload.body,
    serverData: serverData,
    conflictType: determineConflictType(queueItem, serverData)
  };
}

function determineConflictType(queueItem, serverData) {
  if (queueItem.action_type === 'delete' && serverData.exists) {
    return 'delete_vs_edit';
  }
  if (queueItem.action_type === 'update' && serverData.updated_at > queueItem.payload.updated_at) {
    return 'edit_vs_edit';
  }
  if (queueItem.action_type === 'create' && hasDuplicate(queueItem, serverData)) {
    return 'create_vs_duplicate';
  }
  return 'none';
}
```

---

### Conflict Resolution Rules

**Rule 1: Last-Write-Wins (Default)**
- Compare timestamps
- Keep most recent
- Notify user of overwrite

**Rule 2: Deletion Always Wins**
- User intent to delete is final
- Proceed with deletion regardless of server edits

**Rule 3: Field-Level Merge (Profile Only)**
- Merge non-conflicting fields
- Use LWW for conflicting fields
- Trigger side effects (e.g., plan regeneration)

**Rule 4: Duplicate Detection (Creates Only)**
- Check for duplicates within 5-minute window
- If duplicate → Use existing ID
- If not → Create new

### Cache Storage

**Storage Mechanism:**
- AsyncStorage (React Native)
- Namespaced keys: `@cache:<type>:<id>`
- Example: `@cache:meal_plan:week_2024-11-04`

**Storage Limits:**
- iOS: ~10MB typical (no hard limit, but avoid bloat)
- Android: ~6MB typical
- Total cache budget: 8MB max

**Cache Size Management:**
```javascript
async function manageCacheSize() {
  const cacheKeys = await AsyncStorage.getAllKeys();
  const cacheItems = [];

  for (const key of cacheKeys) {
    if (key.startsWith('@cache:')) {
      const data = await AsyncStorage.getItem(key);
      const size = new Blob([data]).size;
      const metadata = JSON.parse(data);

      cacheItems.push({
        key,
        size,
        lastAccessed: metadata.lastAccessed,
        priority: metadata.priority
      });
    }
  }

  // Calculate total size
  const totalSize = cacheItems.reduce((sum, item) => sum + item.size, 0);

  // If over 8MB, evict oldest low-priority items
  if (totalSize > 8 * 1024 * 1024) {
    const sortedByPriority = cacheItems.sort((a, b) => {
      if (a.priority !== b.priority) {
        return a.priority - b.priority; // Low priority first
      }
      return a.lastAccessed - b.lastAccessed; // Oldest first
    });

    let freedSpace = 0;
    for (const item of sortedByPriority) {
      if (totalSize - freedSpace <= 7 * 1024 * 1024) break; // Keep 1MB buffer
      await AsyncStorage.removeItem(item.key);
      freedSpace += item.size;
    }
  }
}
```

**Cache Priority Levels:**
- **P0 (Critical):** Current week plans, user profile
- **P1 (High):** Last 3 weeks history, saved items
- **P2 (Medium):** Weight graph, AI insights
- **P3 (Low):** Recipe images, workout library

### Cache Pre-Warming

**On App Launch:**
```javascript
async function preWarmCache() {
  if (isOnline()) {
    // Fetch and cache critical data in background
    const promises = [
```

## Technical Requirements

### Performance Requirements

**Sync Performance:**
- Initial sync on app launch: <5 seconds (p95)
- Reconnection sync: <10 seconds for 24h offline (p95)
- Background sync: <2 seconds (silent)
- Queue processing: >10 actions/second

**Cache Performance:**
- Cache read: <50ms
- Cache write: <100ms
- Cache eviction: <500ms
- Pre-warming: <3 seconds on app launch

**Offline Performance:**
- Log entry (manual): <200ms
- View cached screen: <100ms
- Search cached history: <300ms

### Memory Constraints

**Queue:**
- Max 1000 queued actions
- Each action ~1-5KB
- Total queue size: ~5MB max

**Cache:**
- Total cache: 8MB max
- Critical data: 4MB reserved
- Optional data: 4MB rolling cache

**Memory Management:**
- Aggressive eviction when approaching 8MB
- Priority-based retention (P0 never evicted)

### Network Optimization

**Request Batching:**
- Batch queued actions (max 50 per batch)
- Single API call: `POST /api/sync/batch`
- Reduces network roundtrips by 90%

**Compression:**
- Gzip all API requests/responses
- Reduces payload size by 70%

**Incremental Sync:**
- Only fetch changed data (delta sync)
- Use `If-Modified-Since` headers
- Reduces bandwidth by 80% for subsequent syncs

**Exponential Backoff:**
- Retry failed requests with backoff: 2s, 4s, 8s
- Prevents server overload
- Max 3 retries per action

### Data Validation

**Queue Validation:**
- Validate payload before enqueue
- Check required fields
- Enforce max queue size (1000 items)
- Reject invalid actions

**Cache Validation:**
- Verify cache integrity on read
- Detect corrupted data
- Fallback to API if cache invalid

**Conflict Validation:**
- Validate timestamps before applying LWW
- Ensure dependencies resolved
- Log conflicts for analytics

### Error Handling

**Network Errors:**
- Timeout (30s) → Retry with backoff
- DNS failure → Show offline banner
- Server 500 → Retry 3x, then queue for later

**Cache Errors:**
- Corrupted cache → Clear and re-fetch
- Out of storage → Evict low-priority items
- Read failure → Fallback to API

**Queue Errors:**
- Invalid action → Skip and log error
- Dependency cycle → Break cycle, log warning
- Max retries exceeded → Move to failed queue, notify user

## Error Handling & Recovery

### Error Types & Recovery

**1. Network Timeout**
- **Scenario:** API request takes >30 seconds
- **Recovery:**
  1. Cancel request
  2. Add to retry queue
  3. Show toast: "Request timed out. Will retry automatically."
  4. Retry with exponential backoff (3x max)

---

**2. Server Error (500, 502, 503)**
- **Scenario:** Backend service down or error
- **Recovery:**
  1. Log error to analytics
  2. Add to retry queue
  3. Show toast: "Server error. Will retry automatically."
  4. Retry 3x with backoff
  5. If still failing → Show message: "We're experiencing issues. Please try again later."

---

**3. Authentication Error (401)**
- **Scenario:** Auth token expired or invalid
- **Recovery:**
  1. Clear auth tokens
  2. Show login screen
  3. Preserve sync queue (don't lose data)
  4. After re-login → Resume sync

---

**4. Validation Error (400)**
- **Scenario:** Invalid data sent to server
- **Recovery:**
  1. Do NOT retry (won't succeed)
  2. Log error for debugging
  3. Remove from queue
  4. Show user-friendly error: "Failed to save [Item]. Please try again."
  5. Keep item in UI, allow manual re-save

---

**5. Conflict Detected**
- **Scenario:** Local and server data both changed
- **Recovery:**
  1. Apply conflict resolution rules (see Conflict Resolution)
  2. Notify user of resolution
  3. Update UI with merged data

---

**6. Storage Quota Exceeded**
- **Scenario:** Device storage full, can't save queue/cache
- **Recovery:**
  1. Evict low-priority cache items
  2. If still full → Show warning: "Storage full. Please free up space."
  3. Disable offline mode until space available
  4. Queue actions in memory (lost on app close)

---

**7. Corrupted Cache**
- **Scenario:** Cache data unreadable or invalid
- **Recovery:**
  1. Delete corrupted cache entry
  2. Re-fetch from API (if online)
  3. If offline → Show empty state with message: "Data unavailable offline."

---

**8. Dependency Cycle in Queue**
- **Scenario:** Item A depends on B, B depends on A (circular dependency)
- **Recovery:**
  1. Detect cycle using topological sort
  2. Break cycle by removing dependency from older item
  3. Log warning for debugging
  4. Proceed with sync

---

### User-Facing Error Messages

**Principles:**
- Clear, non-technical language
- Actionable (tell user what to do)
- Reassuring (data is safe)
- Honest (don't hide errors)

**Examples:**

❌ **Bad:** "NetworkError: ECONNREFUSED at socket.connect"
✅ **Good:** "Can't connect to server. Check your internet connection."

❌ **Bad:** "Sync failed due to timestamp conflict"
✅ **Good:** "Your changes couldn't be saved. Please try again."

❌ **Bad:** "HTTP 401 Unauthorized"
✅ **Good:** "Your session expired. Please log in again."
